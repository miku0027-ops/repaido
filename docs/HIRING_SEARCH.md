# Hiring discovery reads and caching

Public category leaders and live hiring discovery use indexed worker and worker-job lookups instead of loading every worker and job on each request. Worker-funded offers are looked up by worker ID when a profile is built. SQLite has matching expression indexes; Firestore uses its automatic single-field indexes. Final hiring actions recheck availability against current records.

Public city-only leaderboard responses have an eight-second, per-process cache in production. The web app shares a 20-second, per-tab cache when a customer revisits a category and combines simultaneous requests. City-only cards can remain visible for up to two minutes during revalidation; live availability reads always go back to the server. Failed refreshes leave the current visible cards in place with a retry message. Both caches are bounded and expire; neither persists profiles in browser storage. GPS and live availability searches bypass the server cache. Browse results can take up to the cache lifetime to reflect changes.

Catalogue text and public professional text use a snapshot-versioned Bloom filter plus exact prefix postings. Impossible terms skip candidates before costly professional job/review/offer hydration. Normalized synonyms and partial-token scoring match the existing discovery rules. Bloom positives always require an exact posting match; false positives cannot create results. Every addition, deletion, edit or ordering change creates a new content digest and rebuilds the immutable snapshot, so old negative results cannot hide new professionals. The bounded per-process cache retains up to eight small public snapshots, never search history, account data or authorization/availability decisions. Large snapshots fall back to exact matching instead of exceeding the memory budget. Existing social name/handle discovery already uses exact prefix lanes and does not need a Bloom filter ahead of its indexed point lookup.

Verified review confidence continues to shrink sparse averages by `n/(n+5)` and then uses completed work for ties. Scores come from real completed jobs; no invented match percentage, rank or review is added.

The current reads remove global job scans for ordinary city searches, but do not establish million-worker capacity. Strict cross-city nearby browsing still reads the full worker pool, and live hiring still reads all online workers before checking distance. Large city/category pools also require a dedicated search index or materialized candidate index. Before claiming million-user readiness, add that index, backfill existing workers, run representative load tests, and tune Cloud Run concurrency and autoscaling from measured latency and Firestore read costs.
